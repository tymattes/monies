# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Workflow: spec-driven

`specs/brief.md` is the source of truth for product intent. Every feature starts as a numbered spec in `specs/` (copy `specs/_template.md`; process in `specs/README.md`). Don't write feature code without an approved spec, and update the spec's status and acceptance checkboxes as work lands. Documentation is part of every spec: update `README.md` (features, config, commands, deploy notes) and this file in the same PR, and list the changes in the spec's Documentation section.

## Git workflow

Never push directly to `main`. Work on a feature branch, push it, and open a pull request with `gh pr create`; the user merges. Branch names: `<type>/<short-name>`, e.g. `feat/003-households`, `fix/health-timeout`, `chore/...`. One spec per branch/PR where practical, with the spec status update included in the same PR. Commits end with the Co-Authored-By trailer.

## Commands

Stack: Next.js (App Router) + TypeScript + Tailwind, `src/` layout, npm.

- `npm run dev`: dev server on :3000
- `npm run build` / `npm run start`: production build (`output: "standalone"`) and serve
- `npm run lint`: ESLint
- `npm test`: Vitest integration tests against a separate `monies_test` DB on the Compose Postgres (`docker compose up -d db` first; `tests/global-setup.ts` creates and migrates it)
- `npm run test:e2e`: Playwright browser tests (real Chromium, axe accessibility scans) against a throwaway `monies_e2e` database on port 3100; one-time `npx playwright install chromium`; `E2E_PROD=1` runs the production build, `E2E_WEBKIT=1` adds WebKit. `npm run e2e:screenshots` writes light/dark, desktop/phone screenshots of every page to `e2e-screenshots/` (git-ignored)
- `docker compose up --build`: run the full stack (app + Postgres). Needs `.env` copied from `.env.example` with `POSTGRES_PASSWORD` and `BETTER_AUTH_SECRET` set; healthcheck hits `/api/health`
- `docker compose up -d db`: Postgres only, for native `npm run dev` (uses `DATABASE_URL` from `.env`)
- `npm run db:generate` / `npm run db:migrate`: generate migrations from `src/db/schema.ts` / apply them manually

## Architecture

Specs 001-010 are done: header/logo shell, `GET /api/health` (reports DB connectivity, 503 when down), the database foundation, households/auth, categories/budgets, theming, income, bills, the Plan area and Overview, and browser testing. Business logic should go behind API route handlers (`src/app/api/`) so a future iOS app can reuse them.

- Data access: Drizzle ORM over `postgres`. `src/db/schema.ts` holds tables (Better Auth's `user`/`session`/`account`/`verification`, plus `households`, `household_members`, `invites`, `categories`, `budget_allocations`, `income_sources`, `income_amounts`, `income_deposits`, `bills`, `bill_versions`), `src/db/index.ts` exposes lazy `getDb()`/`getSql()` so builds work without a DB. Migrations are SQL files in `drizzle/`, committed.
- Auth: Better Auth (`src/lib/auth.ts`, lazy `getAuth()`), mounted at `/api/auth/[...all]`. Public sign-up is disabled; accounts are only created by `src/lib/accounts.ts` (`insertUserWithPassword`) from first-run setup and invite accept. One household per instance, enforced by a unique constraint on `households.singleton`.
- Every household-scoped route handler calls `requireHousehold(request.headers, { role? })` from `src/lib/household.ts` first; wrap handlers in `route()` from `src/lib/http.ts` for JSON errors. `src/proxy.ts` only does an optimistic cookie check and redirect; it is not authorization.
- Budgets are time-versioned: `budget_allocations` rows are effective from a month onward, and a month's amount is the row with the latest `effective_month` on or before it (`getBudget` in `src/lib/budgets.ts`). Never update or delete past rows; past months are read-only in `setAllocation`. Months are `YYYY-MM` in the API and `YYYY-MM-01` `date` values in the DB (`src/lib/months.ts`); "current month" uses the server `TZ`. Money is integer minor units (`src/lib/money.ts`); the API field is `amountCents` for every currency. Categories are archived via `archived_from`, never deleted.
- Tests that depend on "today" mock `currentMonth` from `@/lib/months` (see `tests/budgets.test.ts`); shared helpers live in `tests/helpers.ts`. Run `npx next typegen` if `RouteContext` types are missing.
- Bills (`src/lib/bills.ts`): recurring costs whose amount, billing period (`interval_months` 1, 3, 6 or 12) and category are versioned together in `bill_versions` (same latest-effective-month and read-only-past rules as budgets). The monthly equivalent (charge / interval, rounded half up) is computed, never stored, in `monthlyEquivalent` and in the SQL of `activeBills`; keep the two in sync (`tests/bills.test.ts` compares them). Every household member can edit any bill; `added_by` is informational and `on delete set null` ("Former member"). `updateCategory` refuses to archive a category while bills use it or will move into it (`countBillsBlockingCategory`). `getBudget` returns per-category `billsCents`/`remainingCents` and `billsTotalCents`/`leftAfterBillsCents`. Routes: `/api/bills`, `/api/bills/[month]`, `/api/bills/items/[id]` (PATCH), `/api/bills/[month]/items/[id]` (PUT).
- Navigation (`HeaderNav`): top-level destinations are Overview (`/`), Plan (opens `/budget`; active on `/budget`, `/bills`, `/income`) and Members. Budget | Bills | Income are tabs of one plan, rendered by `PlanHeader` (title, `PlanTabs`, `MonthNav`, and `PlanSummary` when given data). It is a component each page renders, not a layout, because Next.js layouts cannot read `searchParams` (the selected month). Unallocated is always income minus budgeted, everywhere. On the Budget page `BudgetEditor` renders the summary from its live state; Bills and Income use `getPlanSummary`. The Assign panel is `#assign` on `/budget`. Keep the top level to five destinations or fewer.
- UI tests without a browser: render components with `renderToStaticMarkup` and mock `usePathname` (see `tests/plan-ui.test.tsx`).
- Overview (`/`, `src/lib/overview.ts`, `src/components/overview/`, `GET /api/overview/[month]`): read-only results for a month. `getOverview` is the single source for both the page and the API and composes `getBudget`, `getIncomeMonth` and `getBillsMonth`; never recompute those numbers in a component. Definitions: Unallocated = income minus budgeted (same as the Plan bar); cash flow splits the budget into `Σ min(bills, budgeted)` and `Σ max(budgeted − bills, 0)`. Attention items are computed in `getOverview` (`AttentionCode`), setup prompts and Assign only for editable months. Charts are hand-built and server-rendered (no chart library, no pies or gauges): stacked and bullet bars in CSS using the `--chart-1..4` tokens (`bg-chart-1`), always with a text equivalent (`role="img"` label or the table beside them), never color alone (unallocated is hatched, negative Left has a minus sign). Put chart bars on `--background`, not `--surface` (Dracula red and purple are below 3:1 on the surface).
- Provisional income (spec 010): `getIncomeMonth` sets `provisional` for the current or a later month when a variable income source is active (variable deposits may still arrive), exposed as `incomeProvisional` on the budget, plan-summary and overview data. It changes only wording, tone and severity, never amounts: when provisional, being above income reads "Over recorded income by" in the normal color and the `over_allocated` and `bills_exceed_income` attention items are `info`; with only fixed income they stay red warnings. `category_bills_over_budget` is never softened. Browser tests seed both households (`resetAndSeed` and `resetAndSeedFixedOnly`).
- Assign unallocated (`assignUnallocated` in `src/lib/budgets.ts`, `POST /api/budgets/[month]/assign-unallocated`): adds part or all of the month's unallocated amount to one or more categories (`{ assignments: [...] }`, or `{ categoryId }` for all of it into one) as normal allocations from that month onward, all-or-nothing. It runs in a single transaction holding a `pg_advisory_xact_lock` keyed on household and month, so concurrent assigns serialize (the loser sees unallocated 0 and gets a 400); `tests/assign.test.ts` proves the lock matters. Nothing assigns automatically, by design. The Budget page remounts `BudgetEditor` whenever the server data changes (its `key`), since the editor keeps local state.
- Income (`src/lib/income.ts`): fixed sources keep a time-versioned monthly amount in `income_amounts` (same latest-effective-month rule as budgets, past months read-only); variable sources record actual `income_deposits` counted in the month of `received_on`. `assertCanEdit` allows an owner, or the source's own member; sources whose member was removed have `member_id` null (`on delete set null`) and are owner-only, shown as "Former member". Deposits are only accepted in months where the source is active. `getBudget` also returns `incomeCents` and `unallocatedCents`. Shared validators live in `src/lib/validate.ts`; `MonthNav` is shared by the Budget and Income pages.
- Visual identity (owner-approved): **purple / cream / green**. Dark mode is Dracula, whose deep purple-gray background is the "purple"; light mode is Alucard's warm cream; **green is the brand accent** (the M logo, `--accent`, focus rings). Keep new UI inside this scheme and use the tokens. Dracula purple (`#BD93F9` dark, `#644AC9` light) plus cyan, pink, orange and yellow are the palette's secondary colors, reserved for charts and highlights. Icons live in `src/app/`: `icon.svg` (adapts to the browser's light or dark tab strip), `favicon.ico` and `apple-icon.png` (bright green tile, dark M), all the M from `Logo.tsx`.
- Browser tests (`e2e/`, `playwright.config.ts`): they seed one deterministic household through the app's API (`e2e/support/seed.ts`), sign in via `signIn(page, OWNER)` (API call on the page's context), and wait for hydration with `waitHydrated`. Tests run serially (one worker, one household); specs that change data call `resetAndSeed()` first. Everything destructive goes through `assertScratch` (database name must end in `_e2e`; `tests/e2e-guard.test.ts` covers it). Never point them at the real database or the Docker instance. **After any UI change, run `npm run test:e2e`, run `npm run e2e:screenshots` and look at the images (in both themes and at phone width) before calling the work done, then redeploy Docker.** New pages and features add their own e2e checks in the same PR. `E2E=1` (set only by Playwright) disables the sign-in rate limiter and the Next dev badge; never set it in a real deployment. In phone emulation `window.innerWidth` grows to fit overflowing content, so layout tests compare against the configured viewport width.
- Styling gotcha: `inputCls` includes `w-full`, so a width override on an input must use the important suffix (`w-32!`, `w-auto!`); a plain `w-32` loses to `w-full` and silently makes the input full width.
- Error pages: `src/app/error.tsx` (in the layout) and `src/app/global-error.tsx` (own document; imports `globals.css` and `themeScript`) replace Next's default. They show a digest reference that matches Next's server log line, never the error text. Because React re-renders `<html>` on an error page and drops the `dark` class, `ThemeToggle` re-applies the saved theme in an effect. `/e2e-error` (fails only when `E2E=1`, otherwise 404) exists for `e2e/error-page.spec.ts`, which runs only with `E2E_PROD=1` since error pages render only in production builds. Sign-in, setup and join screens use `AuthCard` (heading, description and form in one card).
- Surface layers (spec 011): from back to front `--page` (the canvas; `body`/`html`), `--background` (**cards**: every panel, list, table, form and the header bar), `--surface-subtle` (table header rows) and `--surface` (total rows). A card is `cardCls` from `ui.ts` (`rounded-xl border border-border bg-background shadow-sm`; add `overflow-hidden` for lists and tables so fills follow the corners). New panels must be cards, never a bare bordered box on the page. Dark uses Dracula's official layers (`#21222C`, `#282A36`, `#343746`, `#424450`). `text-danger` may sit on the page or a card but never on `--surface` or `--surface-subtle` (below 4.5:1 in dark), so no row hover fills. Light `--danger` is `#C8371F`, slightly darker than Alucard's red, for AA on the deeper page.
- Theming: colors come from the tokens in `src/app/globals.css` (`text-muted`, `text-danger`, `text-accent`, `bg-background`, `bg-surface`, `border-border`, `border-border-strong`), never hardcoded and never translucent foreground overlays like `text-foreground/60` or `bg-foreground/5`; `tests/theme.test.ts` enforces WCAG AA contrast for the text tokens and fails on hardcoded colors in `src/`. Dark is the Dracula palette and light is Alucard (Dracula's official light variant). Never put `text-danger` on a `bg-surface` panel (it is below 4.5:1 there in dark). `dark:` follows the `dark` class on `<html>`, set before paint by the inline script in `layout.tsx`. Check new UI in both themes. The theme choice is per device (`localStorage`).
- Removing a member deletes their user row (cascades to sessions and membership). Later tables that reference users should use `ON DELETE SET NULL` or soft-delete to keep history.
- Migrations run automatically at server start via `src/instrumentation.ts` (dev and container). The Dockerfile copies `drizzle/` into the standalone image.
- Keep `README.md` (notably its tech stack table and config table) current when the stack or env vars change.

## Product constraints from `specs/brief.md`

Specs and any later implementation must respect these:

- **Household is the root scope.** Every budget, account, and transaction belongs to a household, not an individual. Households have multiple members, and setup includes creating a household and inviting members.
- **Budgets** are monthly and category-driven. Category allocations change over time, and history must be preserved so past months stay accurate. Model allocations as time-versioned, not as a single mutable value.
- **Income** is set per household member and supports both fixed monthly (salary) and variable (freelance, bonuses, irregular deposits). Owners can edit income for every member; members edit their own.
- **Receipt capture**: photograph a receipt, parse merchant, date, total and ideally line items, then show a review step before saving. Entry should take seconds.
- **Dashboards**: budget vs. actual, category trends, income vs. spend, with household-level and per-member views.
- **API-first architecture**: the web app is first, but the API must let a native iOS app be added later without a rewrite.
- **Self-hosted, open-source intent**: must be simple to deploy and back up, with a documented Docker Compose setup that also works as a Portainer stack.
